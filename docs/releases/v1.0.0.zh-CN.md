# v1.0.0 发布说明（中文）

> 本文件是 GitHub Release `v1.0.0` 正文的中文版。**Release 正文只放英文**，这里只进仓库 / 文档站，
> 不追加进 Release（见 `AGENTS.md`「发布（Release）」）。

## 这是什么

`skill_management` 给 OpenCode 里已安装的 skill 装一个开关：看清装了什么、某个 skill 为什么加载不了、
把它从模型视野里拿掉、再放回来。

停用**不碰任何 skill 文件**：只在全局配置里写**一条** `skill` 权限规则（`effect: "deny"`，
软停用用 `"ask"`）。不删除、不移动、不改写；删掉那条规则，skill 就回到原样。

这是第一个正式版：下面描述的能力在 1.x 内冻结。

## 有哪些功能

| 动作 | 做什么 | 写配置 |
|---|---|---|
| `list` | 列出所有已注册 skill，以及它们**对当前调用者 agent** 的有效状态（`available` / `disabled` / `ask`） | 否 |
| `inspect` | 查单个 skill 为什么（不）可用：命中的是哪条规则、各 agent 的差异、id 是怎么来的 | 否 |
| `disable` | 让它从模型可见列表里消失、并拒绝加载（`effect: "ask"` 则保留在列表里、加载时确认） | 是 |
| `enable` | 删掉挡路的那一条规则，恢复可用（不要求是本工具写的） | 是 |

权限怎么算：宿主读**发起调用的那个 agent** 的规则集，取最后一条命中（`findLast`，支持 `*` / `?`），
**一条都不命中时回退 `ask`，不是 `allow`**。所以 `list` / `inspect` 都按单个 agent 求值，并在输出里写明是哪个 agent。

`disable` 写进去的就是这一行（行尾注释是来源标记，`enable` 靠它定位）：

```jsonc
{ "action": "skill", "resource": "windows-shell", "effect": "deny" } // skill_management
```

`deny` 之后：该 skill 从模型可见列表消失，通过内置 `skill` 工具加载会被拒（`permission.rejected`）。

## 怎么用

```text
skill_management({ action: "list" })
skill_management({ action: "inspect", id: "windows-shell" })
skill_management({ action: "disable", id: "windows-shell" })
skill_management({ action: "disable", id: "windows-shell", dryRun: true })
skill_management({ action: "disable", id: "windows-shell", effect: "ask" })
skill_management({ action: "enable",  id: "windows-shell" })
```

- `id` 是宿主注册表给的主键；`name` 在唯一命中时可作别名（重名会返回候选，不猜）。
- `dryRun: true` 只回显将要写入的行，零写入。
- 写入是原子写（`.tmp` + rename），保留缩进、键顺序、行尾风格（CRLF/LF）与 BOM。备份只留 1 份，位于
  `<config>/skill_management.backups/` —— 它是配置的完整副本，配置文件可能含凭据，介意就删掉。
- 写完之后会 reload 宿主并**轮询**各 agent 规则集，确认改动真的被读入；没读入就回滚文件。
- `enable` 只删该 id 的那一条挡路规则，不要求是本工具写的。定位不到唯一一条时会拒绝并贴出原文；
  挡路的是通配规则、agent 级 `permissions` 或 policy 时只报告、不代改。

## 相对 v0.2.0 的变化

**修复 —— `disable` 用 `effect: "ask"` 时可能什么都没做却报成功。** 旧的回读判据是「调用者的有效效果
**不是** deny」。宿主对无规则命中回退 `ask`；agent 自有规则又可能排在全局规则**之后**把它覆盖成 `allow`
—— 两者都不是 `deny`，于是宿主根本没读进规则也判通过。现在核对「调用者规则集里 `{ skill, id, ask }`
规则的条数确实增加」（输出里会出现 `0 → 1`）。若规则读入了但被后面的 agent 规则覆盖，输出会写明实际效果，
不再谎报"已生效"。

**修复 —— 单行 `permissions` 数组会写出非法 JSON。** 配置写成 `"permissions": [{ … }]` 一行时，
新增规则会把逗号插到新项之后，宿主直接解析不了。现在单行情形也能正确插入。

**修复 —— 损坏的状态文件可能被当成有效记录；坏配置会抛错。** `<config>/skill_management.state.json`
不是合法 JSON、没有 `rules` 数组、或 `version` 未知时，整体判为读不到，`list` 会给出提示而不是静默忽略；
`enable` 遇到语法坏掉的配置文件会明确说"无法解析"，不再抛异常。

**更快。** `list` 不再解析目标配置两遍；glob 匹配在无通配符时跳过正则；严格 JSONC 校验不再把整份文件展开成
字符数组。13.6 KB 配置、29 skills × 12 agents × 10 rules 下实测中位数 **3.72 ms → 2.24 ms**（60 次）。

**1.x 冻结**：四个动作的入参与输出语义、上面的规则形状、同行 marker 注释格式、单文件插件结构。
破坏其中任何一条都要 2.0.0。

**维护**：CI 发布改为幂等 —— 对已发布的版本重跑 publish workflow 会正常退出，不再红叉。

## 怎么下载（三种方式）

**推荐：git spec** —— 不走 npm 注册表、不需要 token。

```pwsh
opencode plugin add github:sogeisetsu/opencode-skill-management
```

```pwsh
# npm
opencode plugin add opencode-skill-management@1.0.0
```

**离线 / 单文件（不碰 npm）**：从本页附件下载 `skill_management.js`，放进 `<config>/plugins/`
（Windows 是 `%USERPROFILE%\.config\opencode\plugins\`，其它平台 `~/.config/opencode/plugins/`）。
宿主启动时扫描该目录，不需要在配置里登记。

```pwsh
opencode plugin list --builtin
# skill_management   local   <config>/plugins/skill_management.js
```

> 必须带 `--builtin`：不带时本地目录插件不会列出，会显示 `No plugins found`。

### 附件说明

| 附件 | 是什么 | 什么时候用 |
|---|---|---|
| `skill_management.js` | 整个插件，单文件 | 直接放进 `<config>/plugins/` —— 不需要 npm / 网络 |
| `opencode-skill-management-1.0.0.tgz` | `npm pack` 出来的 npm tarball | 自行解包、内网镜像、或核对 npm 上究竟发了什么 |

`Source code (zip)` / `Source code (tar.gz)` 是 GitHub 自动打的仓库快照；上面两个才是可安装的产物。

## 环境与验收

- OpenCode V2，实测 **2.0.32**（Windows + Linux）。其它 V2 版本未作承诺 —— 本插件用到的宿主 API
  都有端到端验收覆盖，升级后好复核。
- Node 18+；只用 `node:` 内置模块，无第三方依赖，不调用 shell。
- Windows 与 Linux 上 **248 项断言**全过（`node tools/verify.mjs`）。`disable → 拒载 → enable`
  在新进程里真机复跑：skill 从模型可见列表消失、加载返回 `permission.rejected`、`enable` 后配置文件**逐字节**还原。

**边界**：只写全局配置里的 `skill` 权限规则 —— 不碰项目级配置、不碰 skill 文件、不写 `policies`。
`ask` 是软停用（仍在列表里、每次加载确认）。`list` 的 `state` 列按调用者 agent 求值，默认全拒的子 agent
会显示不同状态，`inspect` 里有逐 agent 表。
